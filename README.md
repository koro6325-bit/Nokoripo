## 1. サービス概要

- **このサービスはどんなサービスか**
  欲しいものから今月の予算を逆算し、毎月の引き落とし時の恐怖をなくすための、貯金が苦手な人専用の「逆算残高メーターアプリ」です。
- **誰の、どんな課題を、どう解決するか**
  キャッシュレス決済の普及により、引き落とし日まで利用額を把握できず毎月ゾッとしている人の課題を、自動連携をあえて排除した「1秒手動入力」と「残高の可視化」によって解決します。

---

## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情

普段の買い物をすべてクレジットカードや電子決済で済ませているが、引き落とし日直前になって明細を確認し、「え、今月こんなに使ってたの！？」と毎月のようにゾッとしていた。家計簿をつけようとしても、細かすぎて3日も持たず、貯金したい気持ちはあるのにいつも口座残高を見て罪悪感に苛まれていた。

### 2-2. なぜそれが「気になった」のか

自分自身が「細かい管理が苦手でズボラな性格」だから。世の中の家計簿アプリは「何にいくら使ったか（食費、日用品など）」の分類ばかりを求めてきて親近感が湧かず、本当に自分が求めている「あといくら使って大丈夫なのか」が直感的に分からないことに強い違和感を覚えた。

---

## 3. 課題の整理

### 3-1. 表に見えている困りごと

キャッシュレス決済の使いすぎで、毎月の引き落とし額を見てゾッとする。家計簿が続かない。

### 3-2. 本当に解決したい課題は何か

- なぜ引き落とし額を見てゾッとするのか？ → リアルタイムで「あといくら使えるか」を把握していないから。
- なぜ把握していないのか？ → 既存の家計簿アプリの入力や、クレカ明細をわざわざ見に行くのが面倒だから。
- なぜ面倒なのか？ → カテゴリ分けなど、自分にとって不要な情報や操作が多すぎて心理的ハードルが高いから。
- **本当に解決したい課題：** 自分の「今月の残りHP（使っていいお金）」がひと目で分からず、主体的なお金のコントロール実感が持てないこと。

---

## 4. 想定ユーザーについて

### 4-1. 想定しているユーザー

「普段の支払いは全てキャッシュレス決済で、貯金はしたいと思っているが、毎月の引き落とし額を把握できずに口座残高を見て落ち込んでいるズボラな会社員」

- **年齢：** 20代中盤
- **理由：** 社会人になり自由に使えるお金が増え、クレカや電子決済を頻繁に使うようになる一方で、まだ大きなお金を管理する習慣が身についていない世代だから。
- **生活・状況設定：** 給与口座から毎月定額が引き落とされるが、毎月「今月は耐えてるだろうか…」と引き落とし日までビクビクして過ごしている。
- **環境設定：** 現金をほぼ持たず、スマホ決済やカード払いが中心。財布を開かないため、お金を使った感覚（痛み）が薄れやすい環境にいる。

### 4-2. 自分とユーザーの距離

- **距離感：** 自分自身
- **理由：** まさに今、自分が毎月キャッシュレス決済の請求額に怯え、家計簿に挫折し、貯金ができずに罪悪感を抱えている当事者だから。

### 4-3. 実際に使われる可能性について

- **最初に使ってくれそうな人：** 自分、および同じようにキャッシュレス決済で使いすぎてしまう友人
- **どんな場面で思い出すか：** レジでカードやスマホ決済をピッと鳴らした直後。
- **代わりに使っているもの：** マネーフォワード（多機能すぎて見なくなった）、スマホの標準メモ帳（計算が面倒でやめた）。
- **置き換えてまで使う理由：** 起動して1秒で「あと何円使えるか」のメーターだけを確認・入力できる圧倒的な手軽さがあるから。

### 4-4. 導入・継続の流れ

- **きっかけ：** 給与日や引き落とし日に「今月こそはお金をコントロールしたい」と思った時。
- **最初の一歩：** ログイン後、今月どうしても買いたいもの（目標）とその予算を1つ登録するだけ。
- **使い続ける理由：** カテゴリ分類の必要がなく、買い物のたびに金額を引くだけで「今月の安全圏」が視覚的に維持される達成感があるから。

## 5. 競合調査

### 5-1. 似たサービスの調査

| サービス名 | 特徴・できること | 本アプリとの違い・優位性 |
| :--- | :--- | :--- |
| **マネーフォワード ME** | 銀行・クレカの自動連携、資産の自動グラフ化、詳細な自動カテゴリ分類。 | 反映に数日のタイムラグがあり「今この瞬間」の残高が不明。情報量が多すぎてズボラな人には心理的ストレスになる。 |
| **Zaim** | 手動入力がしやすく、レシート撮影や詳細な支出分析・グラフ化に強みがある。 | 過去の支出を「分析」することに特化しているため、やはり入力項目が多く挫折しやすい。本アプリは「今使えるお金」のメーターに絞るため手軽。 |

### 5-2. それでも自分が作りたい理由

自動連携は便利だが、反映までに数日のタイムラグがあり、「今この瞬間に使っていい残り金額」が直感的に分からない。また、画面に情報が多すぎて、お金が苦手な人にとっては見るだけで心理的ストレスを感じるため、もっと機能を削ぎ落とした「引き算だけのメーター」が欲しい。

本アプリは、単なる計算機（電卓）やメモ帳とは異なり、「計算結果が自動で保持・合算され続けること」「未来の欲しいもの（目標）と今のお金がメーターで直結していること」「残高マイナス時の自動警告」という、アプリならではの継続性と気づきを提供します。ズボラな人が電卓を開いて手計算する手間のすべてを自動化・簡略化することに本質的な価値があります。

### 5-3. 差別化を「体験価値」で表現する

- **私のアプリの差別化ポイント：**「お金の管理が苦手な人が、買い物の瞬間に1秒手動入力するだけで、今月の引き落とし日に怯えなくて済むようになる体験」

## 6. このサービスで提供したい価値

### 6-1. ユーザーの変化

- **行動の変化：** 買い物のたびに「あといくら枠があるか」をアプリのメーターで確認するようになる。
- **気持ちの変化：** 引き落とし日が近づいてもビクビクせず、安心してお金を使えるようになる。
- **考え方の変化：** 「家計簿＝過去の記録」ではなく、「このアプリ＝未来の欲しいものを叶えるための羅針盤」と捉えられるようになる。

### 6-2. 価値を一文で表す

「このサービスは貯金が苦手な人が、引き落とし日にゾッとすることなく、欲しいもののために計画的にお金を使えるようになるサービス」

## 7. このアプリで実現すること（機能の優先順位）

1ヶ月半の開発期間で確実にMVPをリリースするため、機能を「必須（Core）」と「余裕があれば（Nice to have）」に分類して開発を進めます。

### 7-1. MVP：必須機能（最優先で実装）

- **ユーザー登録・ログイン機能**（Devise）
- **初期設定機能（スライダー/クイック選択）**
  - 「今月の自由なお金」を感覚的に設定できるUI
- **欲しいもの・目標設定機能**（目標名、予算、期限のCRUD）
  - ※システム内で同時にアクティブになる目標は1つのみ
- **今月の利用額 手動入力・削除機能（金額のみ）**
  - 「金額のみ」を即座に入力・削除できるスピードCRUD
  - 「1000円」「500円」などの金額のみのクイック入力ボタン
- **「あといくら使えるか」の逆算残高メーター表示**
  - **演算ロジック：** 今月の使えるお金 ＝ 当月の自由なお金 － 今月分の目標積立額 － 今月のカード利用額の合計
  - **表示仕様：** 残高がマイナス（予算オーバー）になった場合は、メーターにマイナス数値をそのまま表示し、文字色を赤（警告色）に変更
  - **UI/UX世界観：** 初期設定の金額や目的（何に使うか・何を買うか）の入力画面には、親しみやすい吹き出し風のテキストガイド（「何に使うの〜？」「だいたいでOKだよ！」）を配置し、入力作業の心理的ハードルを下げます。※MVPリリース時はCSSによる吹き出しテキスト実装のみとし、キャラクターイラストの配置は実装の進捗（本リリース以降）に合わせて段階的に追加します。

### 7-2. MVP：余裕があれば実装する機能

- **クイック入力ボタンの用途（ラベル）保存**
  - クイック入力時に「コンビニ」「カフェ」などのメモ（用途）も裏側で一緒にDB（`payments.memo`）に自動保存する機能
- **月跨ぎ時の自動リセット・引き継ぎロジック**
  - 処理が複雑化する場合のバックアップ実装（手動リセットボタン等）

### 7-3. 本リリースで作る機能（期間に余裕があれば追加）

- 今月の残り日数を考慮した「1日あたりに使っていい目安心額」の表示
- 目標達成時の演出エフェクト
- キャラクターイラストの追加
- 過去の利用履歴一覧・グラフ機能

## 8. 月が変わったときの挙動

月が替わったタイミング（毎月1日 0:00）で、ズボラなユーザーの手間をなくすために以下の自動処理を行います。

- **今月の自由なお金（`users.monthly_allowance`）：**
  - リセットせず、前月の設定値をそのまま自動引き継ぎます（毎月入力する手間を排除するため）。
- **今月の利用額（`payments`データ）：**
  - メーター計算上は自動リセット（0円スタート）とします。
  - ※データ自体を削除するのではなく、Railsのクエリで「当月分のデータのみを合計してメーターに反映する」ロジックにすることで、データの整合性と将来的な履歴機能への拡張性を担保します。

## 9. このアプリの懸念点とその対策

### 懸念点①

- **何が問題になりそうか：** 自動連携がないため、手動入力すら面倒になってユーザーが離脱する可能性。
- **なぜそう思うか：** そもそもズボラな人をターゲットにしているため、毎回金額を律儀に手入力させる仕様だと電卓の入力コストと変わらなくなってしまう。
- **対策：** 入力コストを極限まで下げるため、金額の「手入力フォーム」だけでなく、「コンビニ（500円）」「カフェ（600円）」「ランチ（1200円）」など、日常のキャッシュレス決済でよく使う金額をワンタップで即時登録できる「クイック入力ボタン」を画面に配置します。ユーザーの操作コストは「ワンタップ」のままズボラ設計を維持しつつ、裏側のデータベース（DB）には「どのボタンが押されたか」のラベル情報（例：memo: "コンビニ"）を自動で一緒に保存する設計とします。これにより、ユーザーに一切の手間をかけさせることなく、本リリース以降の「グラフ・履歴機能」や「AIによる警告メッセージ生成」へのスムーズな拡張性を担保します。

### 懸念点②

- **何が問題になりそうか：** 最初に「今月の自由なお金（元手）」や「目的」を入力する初期設定画面すら、ユーザーがめんどくさく感じて離脱する可能性。
- **なぜそう思うか：** ターゲットが「細かい管理が苦手なズボラな人」であるため、最初の数値入力という行動自体が大きな壁になる。
- **対策：** 「厳密な数字を求めない」というコンセプトをUIの構造とUXライティングで表現します。
  - テキストの手入力を必須とせず、「5万円」「10万円」といった金額をワンタップで選べるボタンや、感覚的に操作できるスライダーUIを採用。
  - 初回登録時はあらかじめ仮の値（例：10万円）を自動セットしておき、「あとからいつでも修正してOK」という状態にすることで、未入力のまま1秒でメイン画面に進める圧倒的に心理的ハードルの低い体験を作ります。
  - 入力フォームの上部には吹き出し風のテキストボックスを配置し、「だいたいでOK！」「何に使う予定〜？」と親しみやすくガイドさせることで、イラスト制作コストを抑えつつ世界観を表現し、スケジュール遅延リスクを徹底的に排除します。

## 11. 技術スタック

### 11-1. 使用予定の技術

- **フレームワーク：** Ruby on Rails
- **DB：** PostgreSQL
- **デプロイ先：** Render（またはFly.io）

### 11-2. 技術選定の比較検討

| **候補** | **採用/不採用** | **理由** |
| --- | --- | --- |
| Ruby on Rails | 採用 | カリキュラムで最も習熟度が高く、残り1ヶ月でMVPを確実に作り切るため。 |
| JavaScript (Hotwire) | 採用 | メーターの動的表示など、最小限の非同期通信の実装に留めるため。 |
| React / Next.js | 不採用 | キャッチアップコストが高く、1ヶ月の納期遅延リスクになるため。本リリース以降に検討。 |

- **今回チャレンジしたい点：** ユーザーが入力した瞬間に、JavaScriptを極力使わずRailsの標準機能（Turbo等）でメーターの数字がパッと変わる快適なUI/UXの実装。
- **不安な点：** 1ヶ月半という短い期間の中での、構築とエラー解消。

### 11-3. キャッチアップ不足の懸念

残り1ヶ月半の開発期間を最優先とするため、今回は慣れ親しんだRailsのMVCモデルのみで実装します。Reactなどのモダンフロントエンド技術は就活も見据えて魅力的ですが、見積もりリスクを避けるため、今回は組み込まずに**本リリース以降の拡張要素**として扱います。

## 12. データベース設計

### ① users テーブル（ユーザー管理）

- ※Deviseが自動で作るものにカラムを追加

| カラム名 | 型 | 役割 |
| :--- | :--- | :--- |
| `id` | integer | 主キー |
| `monthly_allowance` | integer | 今月の自由なお金（例: 100000） |

### ② targets テーブル（欲しいもの・目標）

- ユーザーと「1対多」で紐づきます（`belongs_to :user`）。
- **仕様ルール：** システム内で同時に `is_active: true` になる目標は「常に1ユーザーにつき1つのみ」とします。新しい目標をアクティブにする際、既存のアクティブな目標はモデル側のコールバック処理（`before_save`等）によって自動的に `false`（非アクティブ）へ更新し、データの整合性を担保します。

| カラム名 | 型 | 役割 |
| :--- | :--- | :--- |
| `id` | integer | 主キー |
| `user_id` | integer | 外部キー |
| `name` | string | 目標の名前（例: 「12月の旅行」） |
| `total_budget` | integer | 総予算（例: 50000） |
| `deadline` | date | 目標期限（例: 2026-12-25） |
| `is_active` | boolean | 今月メーターに反映するか（default: true） |

### ③ payments テーブル（カード利用額のメモ）

- ユーザーと「1対多」で紐づきます（`belongs_to :user`）。

| カラム名 | 型 | 役割 |
| :--- | :--- | :--- |
| `id` | integer | 主キー |
| `user_id` | integer | 外部キー |
| `amount` | integer | 使った金額（例: 1500） |
| `memo` | string | 使った場所・用途（例: "コンビニ", "カフェ"） |
| `date` | date | 使用日（default: 今日） |
